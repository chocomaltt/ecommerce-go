Implementation roadmap

Four phases. One proof at a time.

Docs homeAuth guideArchitecture reference

The whole system is built in four phases: Setup → MVP → Fully implement → Prod. A phase is not done until its exit criteria pass. Do not start the next phase with unresolved proof from the previous one.

Phase map

Phase 1 — Setup: the paved road

Goal: one repeatable repository and local environment where a service can be generated, run, observed, tested, and built without inventing new conventions.

Steps, in order

  1. Repository & workspace — moon workspace, go.work, shared tasks (build, test, lint, fmt), and initial modules: edge-api, catalog-service, order-service, common-rpc, common-events, observability platform. Status: done
  2. Contracts — Buf config, lint + breaking tasks, health/catalog/order protobufs. Status: done
  3. Infrastructure — local Compose: PostgreSQL + Kratos (Hydra removed; not needed for first-party flows). Status: done
  4. Trust material — deployments/compose/certs/generate.sh: local CA, workload certificates (edge/identity/order), Ed25519 actor keypair. Status: done
  5. Service conventions — hexagon layout, logrus/slog JSON, graceful shutdown, readiness, Air config. Status: done for edge/identity/order
  6. CI — format, lint, tests, build, Buf checks in one pipeline. Status: pending
  7. Migrations & seeds — explicit migration task per service, idempotent seeds. Status: pending

Definition of done

  • moon ci passes on a clean checkout.
  • Running ./deployments/compose/certs/generate.sh then the three services locally yields a working GET /auth/order-caller.
  • No service imports another service’s internal packages; only common-rpc is shared.
./deployments/compose/certs/generate.sh
cd common-rpc && buf generate && buf lint && go test ./...
cd apps/edge-api && go test -race ./... && go vet ./...

Phase 2 — MVP: one working vertical slice

Goal: prove the architecture under real behavior: an authenticated user can view a product and place an order that is persisted and emits a durable event.

Steps, in order

  1. Order real RPCs — replace the demo GetCaller path with real use cases. Add order.v1 RPCs (CreateOrder, GetOrder) and an order repository port. Keep the existing mTLS + assertion interceptor untouched; the use case enforces ownership: order.CustomerID == actor.UserID. Never put that rule in Edge. Status: next
  2. Catalog service — catalog owns products, SKUs, prices, publication state. Public read through Edge (GET /products), gRPC GetProductForOrder for Order. Status: pending
  3. Order → Catalog checkout read — Order calls Catalog synchronously to obtain sellable product facts, then stores an immutable snapshot (name, unit price, currency, qty) in the order row. Reject unpublished/missing SKU. Status: pending
  4. Persistence — service-owned PostgreSQL repositories and migrations (one DB per service, isolated users). No cross-service DB access. Status: pending
  5. Outbox — write outbox records in the same transaction as order state changes; a publisher forwards them to Kafka later. MVP can ship with outbox table + publisher stub behind a port. Status: pending
  6. Order state machine (no async yet) — PENDING → CONFIRMED for MVP when payment is out of scope; design states so Phase 3 extends them. Status: pending

Definition of done

  • Registered user can create an order through Edge; the order survives a restart (real DB).
  • Different authenticated user gets PermissionDenied on GetOrder; direct non-mTLS caller fails.
  • Historical orders do not change when catalog prices change (snapshot invariant).
  • Each order state change writes exactly one durable outbox record.

Phase 3 — Fully implement: complete business behavior

Goal: the full checkout workflow with durable async steps, compensation, and operational visibility.

Steps, in order

  1. Events & commands — define common-events contracts: commands (ReserveInventory, CapturePayment) and events (OrderCreated, InventoryReserved, PaymentSucceeded, OrderConfirmed). Versioned protos, keys, consumer groups, deadlines. Status: pending
  2. Kafka/Redpanda — local Compose broker, topics, ACLs. Producer = outbox publisher; consumers idempotent. Status: pending
  3. Saga orchestration in Order — durable saga state, one transition at a time, timeout-driven compensation. Define ambiguous-payment precedence. Status: pending
  4. Inventory service — stock, atomic multi-SKU reservation, reservation expiry, movements, outbox. Status: pending
  5. Payment service — provider abstraction (Stripe PaymentIntents), idempotent attempts, webhook verification, reconciliation states. Status: pending
  6. Notification service — terminal event consumers, dedup, retries, provider adapter (email/Mailpit). Status: pending
  7. Observability — Prometheus metrics, structured logs with correlation IDs, OTLP tracing to Tempo, Grafana dashboards + alerts. Status: pending
  8. Idempotency & dedup — client idempotency keys, provider event dedup, inbox/outbox retention, DLQ + redrive runbooks. Status: pending

Definition of done

  • A failed reservation or payment leaves an observable, recoverable order state — never a silent stuck order.
  • Duplicate messages and duplicate webhooks are harmless (idempotent effects).
  • An operator can trace one order across Edge, Order, Inventory, Payment, and Notification from a single correlation ID.
  • Compensation works: inventory released when payment fails; order marked for reconciliation on ambiguity.

Phase 4 — Prod: hardening and controlled go-live

Goal: promote the verified system through Dokploy without exposing private infrastructure or risking irreversible payment/data errors.

Steps, in order

  1. Deployment platform — Dokploy projects/networks/domains/volumes; separate staging and production; managed DB/Kafka decision. Status: pending
  2. Secrets & configuration — inject via secrets manager/env; never commit properties.yaml, private keys, or certs. Status: pending
  3. Workload identity & certificates — replace static dev certs with short-lived certificates and rotation (SPIFFE/SPIRE or a private CA with rotation jobs). Keep per-RPC caller ACLs. Status: pending
  4. Service hardening — TLS 1.3 everywhere, bounded timeouts, readiness probes, resource limits, no admin ports exposed. Status: pending
  5. Browser session hardening — Kratos session as HttpOnly/Secure/SameSite cookie instead of bearer token in JS. Status: pending
  6. Backups & restore — automated PostgreSQL backups, tested restore, retention policy (RPO ≤ 15 min, RTO ≤ 4 h initially). Status: pending
  7. SLOs & alerts — baseline SLIs, error budgets, burn-rate alerts, dashboards; confirm targets with product. Status: pending
  8. Go-live sequence — staging smoke → expand migrations → consumers before producers → internal services → Edge → synthetic checkout → Stripe test/live → low-volume real transaction → observe/reconcile → gradual traffic. Status: pending
  9. Runbooks & on-call — stuck order, provider ambiguity, inventory divergence, DLQ record, telemetry outage; incident ownership. Status: pending

Definition of done

  • A real low-value transaction can be purchased, refunded, observed, reconciled, and audited.
  • Rollback never requires reversing a destructive migration.
  • On-call can diagnose every failure class above within the SLO budget.
  • Certificate/key rotation is exercised and tested, not improvised.

Every change checklist

  1. Write/adjust the proto first if another service needs the capability.
  2. Define inbound/outbound port inside the owning service.
  3. Implement the use case; it must not import transport or database packages.
  4. Implement the adapter and the transport mapping.
  5. Add a unit test near the unit; add integration/E2E tests only when a real boundary is crossed.
  6. Run module tests, race detector, vet, and Buf lint.
  7. Update docs/* if the change alters a documented contract or flow.
