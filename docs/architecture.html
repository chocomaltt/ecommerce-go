01Architectural thesis

An ecommerce platform is not primarily a collection of CRUD endpoints. It is a coordination system for promises: a price was shown, stock was reserved, money was accepted, an order was confirmed, and a customer was informed.

The proposed system uses synchronous gRPC for immediate questions and short commands, directed Kafka commands for durable saga steps, and Kafka events for published business facts. PostgreSQL remains the source of truth for each service. The public network ends at edge-api; every other service is private infrastructure.

A service owns a business decision, its database, and the consequences of changing that decision.
Primary boundary rule

Microservices are justified only when boundaries are explicit. Splitting a codebase into seven binaries without separating ownership creates a distributed monolith: more deployments, more network failures, but the same coupling. This plan therefore treats service boundaries, message contracts, and failure behavior as first-class design material.

Principles

01

One public entry point. Internet traffic reaches Traefik, then edge-api. Databases, Kafka, Prometheus, Loki, Grafana, and internal gRPC endpoints stay private.

02

One owner per fact. Catalog owns product descriptions and list prices. Inventory owns stock. Payment owns provider state. Order owns the customer-visible purchase lifecycle.

03

No distributed database transaction. Cross-service consistency is achieved through state machines, events, idempotency, and compensation—not two-phase commit.

04

At-least-once is normal. Messages may be repeated. Handlers must make repetition harmless.

05

Operational evidence is part of the feature. A checkout is not complete until operators can trace it, measure it, and diagnose its failures.

06

Contracts are shared; business models are not. Protobuf modules describe communication. They must never become a global domain model imported everywhere.

Scope warning Seven services, Kafka, and a full observability stack are expensive for a first milestone. Keep the target architecture, but deliver it as vertical slices. First prove catalog and order behavior; then add authentication, inventory, payment, and notifications.

03Service boundaries

Each service is defined by the business decisions it alone may make—not by a database table or API route.

edge-api

The Edge is the only internet-facing application. It terminates the public API contract and translates public REST requests into private gRPC calls. It asks Identity to resolve client sessions, forwards only Identity-issued actor assertions, propagates request context, and maps internal errors into stable public error responses.

It must not access service databases, implement checkout rules, consume business events, or become a second domain layer.

When Catalog becomes a checkout availability risk

Start with Order calling Catalog synchronously because it is the shortest correct design. If measurements later show that Catalog latency or availability harms checkout, Catalog can publish ProductPublished, ProductPriceChanged, and ProductUnpublished events. Order may then maintain a minimal local sellable-product projection. Do not build this projection speculatively: it introduces replication lag, replay, backfill, and reconciliation work.

identity-service: application boundary around Ory

identity-service is a private gRPC application service. It owns registration/login/logout orchestration, Kratos session resolution, and issuance of short-lived signed internal actor assertions. Only the Edge workload certificate may invoke its RPCs.

Use self-hosted Ory Kratos for identities, credentials, login, registration, recovery, verification, MFA, and sessions. The application never stores passwords or duplicates Ory session state.

For a protected request, Edge sends the client session token to Identity over mTLS. Identity calls Kratos /sessions/whoami, then signs a 60-second Ed25519 actor assertion for the target audience. Edge forwards that assertion—not the Kratos credential—to the destination service over a separate mTLS connection.

ComponentOwnsDoes not ownDecision
Ory KratosIdentity, credentials, self-service flows, MFA, sessions.Application authorization and service-to-service trust.Authentication authority
identity-serviceAuth orchestration and short-lived internal actor assertions.Passwords, credential storage, external session persistence.Private application boundary over mTLS.

Keep a small application-owned customer profile only for commerce-specific data such as addresses or marketing consent. Reference the immutable Kratos identity ID as identity_subject; never duplicate passwords or Ory sessions.

catalog-service

Owns products, categories, variants, SKUs, descriptive attributes, publication state, and list prices. It does not own available stock. During checkout, Order records a snapshot of the purchased SKU, name, unit price, currency, and quantity so historical orders do not mutate when Catalog changes.

order-service

Owns the customer-visible purchase lifecycle and acts as the checkout saga orchestrator. It validates checkout intent, stores order and item snapshots, calculates or verifies totals, persists the current saga step, issues explicit workflow commands, consumes inventory/payment outcomes, chooses compensation, and emits customer-visible lifecycle events through an outbox.

PENDING→ AWAITING_INVENTORY→ AWAITING_PAYMENT→ PAYMENT_RECONCILIATION→ CONFIRMED

Failure branches end in CANCELLED or FAILED. Transitions should be explicit methods or application commands, never arbitrary status updates from handlers.

Cart ownership

Order owns carts for now; do not create a separate cart service. A cart is mutable shopping intent, while an order is an immutable commercial record. Keep them as separate aggregates and tables inside order-service.

carts
- id, user_id, status, currency, version, expires_at, updated_at

cart_items
- cart_id, sku, quantity, observed_unit_price, observed_at

orders / order_items
- immutable checkout snapshot created from the cart

Cart prices are advisory. At checkout, Order revalidates sellability and price against Catalog, calculates the authoritative total, and creates order-item snapshots. Cart mutation uses optimistic versioning so two devices do not silently overwrite each other. Guest carts can later use an opaque signed cart token and merge into a user cart after login.

Future discounts, tax, shipping, and multiple currencies fit through explicit quote components rather than changing stored totals in place:

order_amounts
- merchandise_subtotal_minor
- discount_total_minor
- shipping_total_minor
- tax_total_minor
- grand_total_minor
- currency

order_adjustments
- type: discount | tax | shipping
- code / jurisdiction / description
- amount_minor
- calculation_version

For MVP these extra amounts remain zero and one configured currency is accepted. Later calculators produce a versioned checkout quote; Order snapshots every component. Never recompute historical orders from current tax, coupon, or shipping rules.

inventory-service

Owns on-hand quantity, reserved quantity, stock movements, reservations, reservation expiry, and reservation consumption. The fundamental invariant is:

available_quantity = on_hand_quantity - reserved_quantity
available_quantity >= 0

Reservation operations must use one database transaction and atomic conditional updates or row locks. An expired or cancelled checkout releases its reservation. A confirmed order consumes it.

UPDATE inventory_items
SET reserved_quantity = reserved_quantity + $2
WHERE sku = $1
  AND on_hand_quantity - reserved_quantity >= $2;

-- exactly one affected row means the item was reserved

For a multi-SKU order, sort SKUs deterministically, reserve all rows in that order inside one transaction, and roll back the entire reservation if any SKU is unavailable. This prevents partial order reservations and reduces deadlock risk. A unique reservation-item constraint such as (reservation_id, sku) makes retries harmless.

payment-service

Owns payment attempts, provider references, idempotency keys, webhook verification, authorization/capture/refund state, and reconciliation. Use Stripe PaymentIntents in sandbox/test mode first, then activate live mode only after webhook, reconciliation, refund, and operational checks pass. Money is stored as integer minor units plus ISO currency; floating point is forbidden.

amount_minor = 1099
currency     = "USD"

Immediate capture versus authorize-then-capture

Immediate capture charges the customer as soon as payment succeeds. It is simpler and is the chosen MVP behavior after stock has been reserved. Authorize-then-capture first reserves funds and captures them later—usually when fulfillment is ready. It is useful for physical goods, delayed shipping, split fulfillment, or stock that is not final at checkout, but authorization expiry and partial capture add workflow states.

Design Payment with separate authorized_amount and captured_amount plus explicit commands, while initially configuring Stripe for automatic/immediate capture. This preserves a later migration to manual capture without changing Order’s money representation.

The browser never determines final payment truth. A verified provider response, provider lookup, or verified webhook does. Payment must represent ambiguous outcomes explicitly:

PENDING→ PROCESSING→ SUCCEEDED FAILED UNKNOWN REQUIRES_RECONCILIATION

A provider timeout is not proof of failure: the provider may have processed the request while the response was lost. Keep the original provider idempotency key, query provider truth or wait for a verified webhook, and reconcile asynchronously. Order must not release inventory merely because the synchronous payment response timed out.

notification-service

Consumes final business events and translates them into delivery requests. It owns templates, provider integration, deduplication, delivery attempts, and—when required—retry policy. Notification failure must not roll back a confirmed order.

3 Catalog answers “what is this item and what is its price?” Inventory answers “can this quantity be promised now?” Keeping these decisions separate prevents stock concerns from infecting product publishing.

4 A notification is a consequence, not the transaction. Email outages should be visible and retried, but must not make the purchase disappear.

Hexagonal architecture is a dependency rule: business behavior depends on ports; adapters depend on business behavior. Folder names merely make the rule visible.

Dependency direction

                                                        ▲

                                                  PostgreSQL adapter

Kafka consumer ─────► application service ───────► event/outbox port

main/app wiring imports all sides and connects them.

Boundary rules

  • Domain/application packages never import Gin, gRPC generated server types, Kafka clients, SQL drivers, GORM, environment loaders, or HTTP DTOs.
  • Transport adapters own request parsing and response mapping.
  • Persistence adapters translate database rows and infrastructure errors into application concepts.
  • Ports are defined where they are consumed. Do not create a global interfaces package.
  • Create an interface only when the application consumes a capability from outside its boundary or when multiple implementations are meaningful.
  • The composition root owns resource startup and shutdown: DB pools, Kafka clients, gRPC connections, HTTP servers, workers, and telemetry providers.

Lessons from the inspected repository

Repository interfaces beside core servicesPorts are mockable and owned near use cases.Keep infrastructure errors such as gorm.ErrRecordNotFound out of core.

Minimal ports. A broad repository interface copied across layers is ceremony. Prefer a capability named for the use case: SaveOrder, FindOrder, ReserveStock.

Composition is allowed to know everything. The process entrypoint is where concrete adapters meet abstract ports. It is not domain code.

05Checkout saga

Checkout is a distributed state machine with one explicit coordinator. order-service owns saga progress and compensation; Inventory and Payment remain authoritative for their own decisions.

Why orchestration here

Pure event choreography is attractive when reactions are independent, but a critical checkout path has ordering, timeout, compensation, and ambiguity rules. If Inventory triggers Payment directly and Payment triggers Order indirectly, the workflow is spread across consumers and becomes difficult to inspect or change. Order therefore sends commands and records each expected reply. Choreography remains appropriate after a final fact such as OrderConfirmed, where Notification, analytics, and future fulfillment can react independently.

order-service                    inventory-service             payment-service
     │ ReserveInventory command        │                              │
     ├─────────────────────────────────►│                              │
     │ InventoryReserved event         │                              │
     │◄─────────────────────────────────┤                              │
     │ CapturePayment command          │                              │
     ├───────────────────────────────────────────────────────────────►│
     │ PaymentSucceeded event          │                              │
     │◄───────────────────────────────────────────────────────────────┤
     │ ConfirmReservation command      │                              │
     ├─────────────────────────────────►│                              │
     │ records CONFIRMED and publishes OrderConfirmed                 │

Durable happy path

  1. The client submits checkout to Edge with an idempotency key.
  2. Edge asks Identity to resolve the client session, then calls Order over gRPC with a deadline and target-bound actor assertion.
  3. Order obtains authoritative product/price data from Catalog, records immutable line-item snapshots, creates the order and saga row, and inserts ReserveInventory into its outbox in the same transaction.
  4. The Order publisher sends the command to Kafka, keyed by order_id.
  5. Inventory consumes the command, deduplicates by message_id, atomically reserves every SKU, and emits either InventoryReserved or InventoryRejected.
  6. Order consumes InventoryReserved, records the reservation ID, advances to AWAITING_PAYMENT, and writes CapturePayment to its outbox in the same transaction.
  7. Payment consumes the command and uses a stable provider idempotency key derived from the payment attempt—not from a retry count.
  8. Payment emits PaymentSucceeded, PaymentFailed, or keeps an ambiguous attempt in reconciliation without publishing false failure.
  9. Order consumes success, writes ConfirmReservation, transitions to CONFIRMED, and emits OrderConfirmed according to the chosen confirmation invariant.
  10. Notification and other independent consumers react to OrderConfirmed. Their failures never reverse the order.

Compensation and ambiguity

InventoryRejected
  └──► Order CANCELLED (reason: insufficient_inventory)

InventoryReserved → definitive PaymentFailed
  ├──► Order writes ReleaseInventory command
  └──► Order CANCELLED only after compensation is durably requested

InventoryReserved → provider timeout / lost response
  ├──► Payment UNKNOWN or REQUIRES_RECONCILIATION
  ├──► keep reservation until a bounded payment-resolution deadline
  └──► provider lookup/webhook decides SUCCEEDED or definitive FAILED

Notification failure
  └──► retry/quarantine notification only; order remains CONFIRMED

Saga persistence

checkout_sagas
- order_id               text primary key
- state                  text not null
- expected_message_type  text null
- reservation_id         text null
- payment_id             text null
- deadline_at            timestamptz null
- version                 bigint not null
- last_error_code        text null
- updated_at              timestamptz not null

Each transition checks the current state and expected message, updates the saga with optimistic versioning or row locking, and creates the next outbox message in one transaction. Late, duplicate, or out-of-order results are logged and ignored or reconciled according to explicit transition rules.

Client response semantics

The initial checkout endpoint should return an accepted order representation once Order has durably recorded the request. It should not keep the HTTP request open while inventory, payment, and notification finish. The client observes progression through order polling, server-sent events, WebSocket updates, or push notifications. Polling is the simplest correct first choice.

Recommended response:

HTTP/1.1 202 Accepted
Location: /v1/orders/ord_...

{
  "order_id": "ord_...",
  "status": "awaiting_inventory",
  "created_at": "..."
}

Timeouts and abandonment

Inventory reservations must expire, but expiry must account for payment ambiguity. A scheduled worker finds expired active reservations and requests release only when Order/Payment policy says no successful or unresolved payment remains. The timeout value is a product decision and operational parameter, not a hard-coded handler constant.

DeadlineOwnerAction after expiry
Inventory command responseOrderRetry safely, inspect consumer lag, then quarantine/stall rather than assuming rejection.
Reservation lifetimeInventoryEmit expiry intent; coordinate with Order when payment may be unresolved.
Payment resolutionPaymentQuery provider, await verified webhook, then mark success or definitive failure.
Saga maximum ageOrderRaise operational alert and run reconciliation; do not silently force a guessed outcome.

5 Returning 202 Accepted reflects reality: the checkout request is durable, but the distributed workflow is not yet complete.

6 A rare race exists when payment succeeds near reservation expiry. The state machine must define precedence and reconciliation. Provider truth and recorded timestamps should make the resolution deterministic.

06Kafka commands and events

Commands request one owner to perform a workflow step. Events are immutable statements of facts that already happened. Keeping them separate makes responsibility, retries, and failure behavior visible.

Message semantics

KindNamingAudienceExamples
CommandImperative verbOne logical service ownerReserveInventory, CapturePayment, ReleaseInventory
EventPast-tense factZero or more consumersInventoryReserved, PaymentSucceeded, OrderConfirmed

A command is not proof that work occurred. Only the corresponding result event records the outcome. Consumers must never infer “payment succeeded” from seeing CapturePayment.

Initial topics

commerce.inventory.commands.v1   # consumed by inventory-service group
commerce.payment.commands.v1     # consumed by payment-service group
commerce.order.events.v1
commerce.inventory.events.v1
commerce.payment.events.v1

Begin with domain-level topics rather than one topic per message. Use order_id as the key for checkout messages so Kafka preserves per-order ordering within a partition. A command topic has one logical consumer group; replicas share that group. Independent event consumers use separate groups.

Common message metadata

message MessageMetadata {
  string message_id      = 1;  // unique delivery/deduplication identity
  string message_type    = 2;
  uint32 message_version = 3;
  string created_at      = 4;
  string producer        = 5;
  string correlation_id  = 6;
  string causation_id    = 7;
  string aggregate_id    = 8;  // order_id for checkout
  string reply_by        = 9;  // commands only; business deadline
}

// Metadata may wrap a typed oneof payload or accompany a concrete
// versioned Protobuf message. Do not use untyped JSON maps.

correlation_id links an end-to-end business interaction. causation_id identifies the command or event that directly caused this message. message_id drives transport deduplication; business keys still protect external effects.

Workflow vocabulary

OwnerConsumes commandsPublishes result/fact events
InventoryReserveInventory, ReleaseInventory, ConfirmReservationInventoryReserved, InventoryRejected, InventoryReleased, InventoryReservationConfirmed, InventoryReservationExpired
PaymentCapturePayment, RefundPaymentPaymentSucceeded, PaymentFailed, PaymentRequiresReconciliation, PaymentRefunded

Command result rules

  • Every command declares its target aggregate, idempotency identity, schema version, and business deadline.
  • The target emits one durable result fact or records an explicitly unresolved state.
  • A timeout waiting for a result is not itself a negative business result.
  • Replayed commands retain their original message_id, key, correlation, and causation metadata.
  • Order stores which result type it expects so unrelated, late, or out-of-order messages cannot advance the saga.

Names are initial contract decisions. Do not add a consumer to an existing group unless replicas are sharing the same logical work; independent business reactions need independent groups so each receives the event.

Contract discipline

  • Protobuf package names include versions: commerce.order.events.v1.
  • Never reuse a removed field number. Reserve it.
  • Additive optional fields are preferred. Breaking semantic changes require a new event version.
  • Consumers ignore unknown fields and event types they do not own.
  • Events describe facts, not vague mutations. Prefer PaymentSucceeded over PaymentStatusChanged.
  • Do not place secrets, raw card data, passwords, or unnecessary personal information in events.

Common Events is a wire library. Generated protobuf types may be shared. Domain entities, validation rules, and service errors remain private.

Schema registry? Buf provides source contract discipline. A runtime Kafka schema registry can be added when independent teams or non-Go consumers make compatibility enforcement operationally necessary.

07Outbox and idempotency

The outbox closes the gap between a committed database change and a message that must eventually be published. Idempotency closes the gap created when that message is published more than once.

Outbox record

outbox_events
- id                uuid primary key
- aggregate_id      text not null
- event_type        text not null
- event_version     integer not null
- topic             text not null
- message_key       text not null
- payload           bytea not null
- created_at        timestamptz not null
- published_at      timestamptz null
- attempts          integer not null default 0
- last_error        text null

The domain mutation and outbox insert happen in one PostgreSQL transaction. A background publisher claims unpublished rows in bounded batches, publishes them, and marks them published.

SELECT ...
FROM outbox_events
WHERE published_at IS NULL
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 100;

SKIP LOCKED permits multiple publisher replicas without publishing the same claimed row concurrently. It does not create exactly-once delivery: a process can publish successfully and crash before setting published_at.

Consumer inbox / processed events

processed_events
- consumer_name     text not null
- event_id          uuid not null
- processed_at      timestamptz not null
- primary key (consumer_name, event_id)
  1. Begin a database transaction.
  2. Insert (consumer_name, event_id).
  3. If the unique constraint reports a duplicate, commit/acknowledge without repeating work.
  4. Apply the business mutation.
  5. Insert resulting outgoing events into the local outbox.
  6. Commit the database transaction.
  7. Commit the Kafka offset only after the database commit succeeds.

Retention and cleanup

Both tables require bounded, observable cleanup jobs. Cleanup runs in small batches to avoid long locks and WAL spikes.

DataMinimum retention basisCleanup rule
Unpublished outboxNever age-deleteAlert on age/attempts; repair or quarantine with an audit record.
Published outboxOperational replay/audit requirementArchive if required, then delete rows older than the approved window in bounded batches.
processed_eventsMaximum Kafka retention + maximum manual replay horizon + safety marginDelete only after an event can no longer be legitimately replayed. Otherwise old replay can repeat effects.
Provider webhook IDsProvider retry/replay horizon + safety marginRetain long enough to reject delayed duplicates.

Expose cleanup duration, deleted-row count, failures, table size, and oldest-row age as metrics. Payment and security audit data must follow legal/business retention and may need immutable archival rather than deletion.

Business idempotency

Event deduplication is necessary but not sufficient. External providers and public commands need business keys:

  • Checkout accepts a client idempotency key scoped to user/account.
  • Inventory enforces one active reservation per order/SKU decision.
  • Payment sends a stable provider idempotency key per payment attempt.
  • Webhooks deduplicate by provider event ID.
  • Notifications deduplicate by notification type and business aggregate when duplicate delivery is unacceptable.

7 “Exactly once” is not a useful end-to-end promise once a database, Kafka, and an external payment provider participate. Durable at-least-once transport plus idempotent effects is the practical model.

08PostgreSQL ownership

Database-per-service means exclusive logical ownership. It does not require seven PostgreSQL servers on day one.

Use one PostgreSQL cluster initially, with separate databases, users, passwords, and migration histories. Services must not query or write another service’s database. Cross-service data arrives through APIs or events.

DatabaseOwned recordsCritical constraints
kratos_dbKratos-owned identities, credentials, and sessionsManaged only by Kratos migrations; isolated users and backups.
catalog_dbProducts, categories, variants, pricesUnique SKU; currency/amount validity; publication invariants.
order_dbCarts/items, orders/item snapshots, amount adjustments, saga/state history, outbox/inboxCart optimistic version; valid states; positive quantities; non-negative money; idempotency key uniqueness.
inventory_dbStock, reservations, movements, outbox/inboxNon-negative quantities; reservation uniqueness; valid expiry/state combinations.
payment_dbAttempts, provider events, refunds, outbox/inboxProvider reference uniqueness; currency/amount validity; webhook deduplication.
notification_dbDeliveries, attempts, deduplicationDelivery identity uniqueness where required.

Migrations

Migrations live inside the owning service and run as a controlled deployment task. Application replicas must not all race to migrate on startup. Migrations should be forward-compatible with the currently running and immediately previous application deployment during rolling updates.

Recommended discipline:

  1. Expand: add nullable columns/tables/indexes without breaking old code.
  2. Deploy code that writes/reads the new shape.
  3. Backfill if required.
  4. Contract: remove old columns only after no deployed version uses them.

No cross-service foreign keys. An order.user_id is an external Kratos identity reference, not a database FK to kratos_db.

DB constraints matter. Application validation improves errors. Constraints protect truth under races, bugs, retries, and manual operations.

Prometheus, Loki, Grafana, and distributed tracing form one diagnostic system. They should share labels and identifiers so an operator can move from a symptom to the affected request, event, order, and service.

Metrics architecture

Every Go service exposes a private /metrics endpoint. Prometheus scrapes it over the internal network. The endpoint must not be published by Traefik.

Start with RED metrics for request-driven services:

  • Rate: requests per second by service, method, route template, and status class.
  • Errors: failed request rate by stable error category.
  • Duration: latency histogram by service and operation.

Use USE metrics for resources:

  • Utilization: DB pool usage, CPU, memory, goroutines.
  • Saturation: DB wait count/time, Kafka lag, worker queue depth.
  • Errors: connection failures, publish failures, scrape failures.

10Reliability and failure policy

Reliability comes from bounded waiting, controlled retry, explicit terminal states, and repair mechanisms—not from assuming dependencies remain available.

Timeouts

Every network call carries a context deadline. The Edge public timeout must be longer than its internal gRPC deadline, leaving enough time to map and return errors. Database statements use contexts. Kafka shutdown drains or stops workers within a bounded grace period.

Retries

  • Retry only transient failures.
  • Use exponential backoff with jitter.
  • Cap attempts and total retry duration.
  • Retry non-idempotent operations only with a stable idempotency key.
  • Do not stack retries at every layer; compounded retries amplify outages.

Retry and dead-letter ownership

A dead-letter topic is a quarantine mechanism, not a trash bin. Each consuming service owns error classification, retry limits, DLQ dashboards, and a runbook. The platform/on-call operator executes redrive tooling; the service owner approves replay after fixing the cause.

FailureActionExample
Transient infrastructureBounded retry with exponential backoff and jitterDatabase connection reset, broker leader movement
Dependency unavailablePause/back off; alert on lag and agePayment provider outage
Invalid or unsupported messageQuarantine immediately; no hot-loop retryUnknown required schema semantics
Business rejectionPublish a typed negative result, not DLQInsufficient inventory, definitive payment decline
Unknown side effectReconcile before retry or compensationProvider timed out after receiving capture

Quarantined records preserve original topic, partition, offset, key, headers, payload, message ID, consumer, error code, stack/cause summary, attempt count, and first/last failure times. Redrive must:

  1. Record operator, approver, reason, selected messages, and destination.
  2. Preserve original key and semantic metadata so ordering and deduplication still work.
  3. Replay a small canary batch first.
  4. Verify consumer success, resulting state, lag, and absence of duplicate external effects.
  5. Audit the final replay outcome and leave failed records quarantined.

Reconciliation

Payment requires a scheduled reconciliation process. It compares local attempts with provider truth and repairs missing webhook outcomes or ambiguous timeout results. Use the same provider reference and idempotency key; never create a second charge merely because the first response was lost. Inventory requires reservation expiry. Order requires a stuck-order detector. These background repair loops are part of the system, not optional cleanup.

PROCESSING + provider success       → SUCCEEDED → PaymentSucceeded
PROCESSING + definitive decline     → FAILED    → PaymentFailed
PROCESSING + timeout/no provider ID → UNKNOWN   → retry provider lookup
UNKNOWN + verified webhook success  → SUCCEEDED → PaymentSucceeded
UNKNOWN beyond operations deadline  → REQUIRES_MANUAL_REVIEW

No UNKNOWN transition directly releases inventory.

Graceful lifecycle

  1. Receive termination signal.
  2. Mark readiness false so new traffic stops.
  3. Stop accepting new HTTP/gRPC work.
  4. Stop claiming new Kafka/outbox work.
  5. Allow in-flight transactions to finish within a deadline.
  6. Flush telemetry.
  7. Close Kafka, gRPC, and database resources.

Circuit breakers. Add only after real failure behavior demonstrates benefit. Deadlines, bounded concurrency, and retry discipline are the first line of defense.

11Security model

The public trust boundary ends at Edge, but every internal service still validates that requests arrived through authenticated, controlled channels.

Identity flow

  1. Kratos authenticates the user and issues a session token.
  2. Edge calls identity-service.ResolveSession over mTLS. Identity verifies the session through Kratos /sessions/whoami.
  3. Identity signs an audience-bound, short-lived Ed25519 actor assertion. Edge cannot mint or alter it.
  4. Edge opens gRPC with its workload certificate and forwards the assertion. The target verifies the certificate chain, expected Edge identity, assertion signature, issuer, audience, and expiry.
  5. Only then does domain code receive actor context; it still enforces ownership and business authorization.

Implemented Edge → Order example

GET /auth/order-caller
Authorization: Bearer <kratos-session-token>

Edge:
1. mTLS → identity.v1.IdentityService/ResolveSession
2. Identity → Kratos /sessions/whoami
3. Identity returns an Ed25519-signed, 60-second assertion (aud=order-service)
4. mTLS gRPC → order.v1.OrderIdentityService/GetCaller
5. Edge forwards only Authorization: Bearer <internal-assertion>

Order:
1. Require and verify the Edge workload certificate
2. Reject every other workload identity
3. Verify assertion signature, issuer, audience, and expiry
4. Put verified actor context into the Order use case

The reference implementation lives in apps/identity-service, apps/edge-api/internal/adapter/identitygrpc, apps/edge-api/internal/adapter/ordergrpc, apps/order-service/internal, and common-rpc/proto/{identity,order}/v1. Local certificates and the Ed25519 signing keypair are generated by deployments/compose/certs/generate.sh.

Controls

  • TLS at Traefik and mandatory mTLS for internal gRPC. Private networking is defense in depth, not caller authentication.
  • Kratos owns password hashing, recovery, verification, MFA, session lifecycle, and credential policy.
  • Payment card data handled by provider-hosted/tokenized flows; do not store PAN/CVV.
  • Webhook signatures verified against raw request bodies and provider timestamps.
  • Secrets injected through Dokploy secrets/environment, never committed.
  • Database users limited to their owned database.
  • Kafka ACLs restrict producers and consumer groups when supported.
  • Logs redact authorization headers, cookies, passwords, tokens, card details, and sensitive personal fields.
  • Traefik enforces request body limits and coarse rate limits; Edge enforces identity-aware policy where necessary.

Two identities. Kratos identifies the user. Workload mTLS identifies the calling service. Identity-issued actor assertions carry the verified user identity to the target service.

15Verification strategy

Test business invariants and failure boundaries. Avoid spending most of the suite on generated protobufs, trivial getters, or behavior guaranteed by Go’s type system.

Test layers

LayerPurposeExamples
Domain/applicationFast verification of state transitions and policies using small fake ports.Invalid order transitions, money rules, inventory decisions.
Adapter integrationVerify real PostgreSQL transactions, constraints, SQL mapping, and Kafka serialization.Concurrent reservation, outbox claim, duplicate inbox insert.
ContractProtect protobuf compatibility and transport mapping.Buf lint/breaking checks, gRPC status mapping.
Workflow integrationProve a small number of cross-service business journeys.Successful checkout, inventory rejection, payment compensation.
OperationalProve health, telemetry, shutdown, and deployment assumptions.Metrics emitted, trace propagated, logs correlated, SIGTERM drained.

Critical scenarios

  • Successful checkout reaches CONFIRMED and consumes inventory.
  • Insufficient inventory cancels the order without attempting payment.
  • Definitive payment failure causes Order to request reservation release and then reach the defined cancellation state.
  • Provider timeout enters reconciliation and does not release stock or create a second charge.
  • A late success webhook resolves an ambiguous payment exactly once.
  • Concurrent multi-SKU reservations are all-or-nothing and avoid deadlocks through deterministic SKU ordering.
  • Duplicate ReserveInventory does not reserve twice.
  • Duplicate PaymentSucceeded does not confirm twice or duplicate effects.
  • Outbox publish succeeds, process crashes before marking, and replay remains safe.
  • Consumer transaction commits, offset commit fails, and redelivery remains safe.
  • Reservation expires and restores available stock.
  • Payment webhook is duplicated or arrives out of order.
  • A stuck-order reconciliation job identifies and repairs or quarantines the workflow.
  • DLQ canary redrive preserves keys/headers, is audited, and creates no duplicate external effect.
  • Outbox/inbox cleanup retains deduplication through the maximum replay horizon.
  • Trace ID connects Edge, gRPC, Kafka, consumer logs, and relevant spans.

Real dependencies selectively. PostgreSQL concurrency and Kafka offset behavior are integration concerns. Mocks cannot prove them.

Setup phase — establish the paved road

  4. Create local Compose for PostgreSQL, Ory Kratos, and the active observability components. Generate development mTLS certificates; delay Kafka until checkout needs it.

  6. Standardize log/slog JSON, correlation IDs, Prometheus endpoints, OpenTelemetry resource attributes, /live, /ready, graceful shutdown, and Air configuration.

Exit criteria

  • moon run infra:up starts healthy dependencies from a clean machine with documented prerequisites.
  • Edge calls Order over mTLS; Order rejects missing or wrong workload certificates.
  • Kratos login produces a session token; Identity resolves it and issues a target-bound actor assertion; Edge forwards that assertion to Order without forwarding the user credential.
  • All migrations, generation, verification, build, shutdown, and destructive reset tasks are documented and runnable.
PHASE 2

MVP phase — complete one safe purchase

Goal: a user can authenticate, browse products, manage a cart, submit checkout idempotently, reserve stock, pay with Stripe test mode, and observe a confirmed or cancelled order.

Implement in order

  1. Catalog: categories, products, variants/SKUs, publication state, one configured currency, list/read/admin mutation APIs, migrations, and seed data.
  2. Order cart: create/read/update/delete cart items, optimistic cart version, cart expiry, ownership checks, and Catalog price revalidation.
  3. Order creation: immutable item/price snapshots, zero-valued future discount/tax/shipping components, checkout idempotency key, 202 Accepted, polling endpoint, and state history.
  4. Add Redpanda/Kafka through Dokploy-compatible Compose, command/event Protobufs, Order outbox publisher, inbox deduplication, and consumer lag/outbox dashboards.
  5. Inventory: stock records, all-or-nothing sorted multi-SKU reservation, expiry, release/confirm commands, and concurrency integration tests.
  6. Payment: Stripe test PaymentIntent with immediate capture after reservation, stable idempotency key, signed webhook verification, unknown/reconciliation states, provider lookup worker, and refund capability.
  7. Order saga: durable expected-step state, command publication, result handling, compensation, stuck-saga detector, and customer-visible terminal outcome.
  8. Notification: consume OrderConfirmed/OrderCancelled, send through Mailpit locally, and deduplicate delivery.

MVP restrictions

One warehouse, one configured currency, no discounts, no calculated tax, no shipping-rate engine, no partial fulfillment, and immediate capture. The schema already stores currency and amount components so these restrictions do not corrupt future expansion.

Exit criteria

  • Happy path and inventory rejection work end to end through Edge.
  • Definitive payment failure releases inventory; ambiguous timeout does not.
  • Duplicate checkout, Kafka message, and Stripe webhook produce no duplicate order, reservation, or charge.
  • Every checkout is diagnosable by correlation ID, order ID, metrics, logs, and trace.
PHASE 3

Fully implemented — expand commerce capabilities

Goal: complete the planned domain and operational features while preserving old order truth and contract compatibility.

Implement by business priority

  1. Discount adjustments: coupon definitions, eligibility, usage limits, deterministic calculation, and immutable order adjustment snapshots.
  2. Tax: address/jurisdiction inputs, provider or internal calculator port, quote version, line-level tax breakdown, and refund tax treatment.
  3. Shipping: customer addresses, shipping methods/rates, shipment cost snapshots, and eventual fulfillment boundary when actual shipment work exists.
  4. Multiple currencies: Catalog price books, checkout currency selection, no implicit floating-point conversion, provider-supported currency validation, and currency-specific refunds/reporting.
  5. Payment evolution: manual authorize/capture when fulfillment requires it, partial captures/refunds, authorization-expiry handling, and stronger reconciliation dashboards.
  6. Customer experience: guest-cart merge if needed, saved addresses, order history, cancellation/refund requests, and notification preferences.
  7. Operations: admin stock adjustments with audit records, DLQ canary redrive tool, retention jobs, runbooks, SLO burn alerts, load tests, and failure exercises.

Extraction rule

Keep carts inside Order and one-warehouse inventory until ownership, independent scaling, fault isolation, or fulfillment requirements justify extraction. Add a separate pricing, tax, shipping, cart, or fulfillment service only when a measured boundary exists—not merely because large companies have one.

Exit criteria

  • Every enabled capability has a versioned contract, migration, invariant tests, dashboard, alert/runbook, and rollback strategy.
  • Historical orders never change when products, prices, discounts, taxes, exchange assumptions, or shipping rules change.
  • Load and failure tests meet approved SLOs with no unexplained money or inventory divergence.
PHASE 4

Deployment phase — controlled real transactions

Goal: promote the verified system through Dokploy without exposing private infrastructure or risking irreversible payment/data errors.

Implement in order

  1. Create separate staging and production Dokploy projects, networks, domains, volumes, credentials, Stripe accounts/keys, Ory projects/clients, an internal certificate authority, and Grafana access.
  2. Deploy PostgreSQL and Redpanda/Kafka with persistent storage, resource limits, monitoring, automated backups, and tested restore instructions. Prefer managed equivalents if real revenue exceeds your ability to operate them.
  3. Deploy Loki, Grafana, Alloy, Prometheus, Tempo, and OTel Collector privately; expose Grafana only behind strong authentication.
  4. Deploy Kratos at auth...; keep its admin API private; configure redirects, SMTP, MFA, backups, and secret rotation.
  5. Run expand migrations as explicit jobs. Deploy consumers before producers when new messages are introduced.
  6. Issue short-lived workload certificates, deploy internal services with mandatory mTLS and per-RPC caller policy, then deploy Edge. Publish only Edge, required Kratos public endpoints, narrowly routed Stripe webhooks, and protected Grafana.
  7. Run staging smoke, saga, duplicate, compensation, backup-restore, shutdown, and DLQ replay checks. Then use Stripe live-mode readiness and webhook checks.
  8. Start production with low limits and manual observation. Confirm dashboards, SLOs, alerts, reconciliation, refunds, and support/runbook ownership before increasing traffic.

Release sequence

backup/restore proof
  → expand migrations
  → compatible consumers
  → internal services
  → edge-api
  → synthetic checkout
  → Stripe/webhook verification
  → low-volume real transaction
  → observe and reconcile
  → gradual traffic increase

Exit criteria

  • A real low-value transaction can be purchased, observed, refunded, reconciled, and audited.
  • Rollback does not require reversing a destructive migration.
  • On-call knows how to diagnose a stuck order, provider ambiguity, inventory divergence, DLQ record, and telemetry outage.

Exit criteria. Each phase ends with a working business path and operational proof—not only folders, generated clients, or deployment manifests.

Resolved scope and safe defaults

  1. Intent: learning first, but implementation must be capable of controlled real transactions.
  2. Identity: self-hosted Ory Kratos for authentication; Identity issues short-lived internal actor assertions. No custom password implementation.
  3. Payment: Stripe PaymentIntents, immediate capture for MVP after inventory reservation. Authorize-then-capture remains a supported later evolution for fulfillment.
  4. Inventory: one warehouse initially.
  5. Commerce scope: discounts, tax, shipping, and multi-currency are not MVP features, but immutable amount components and adjustments are reserved in the model.
  6. Cart: Order owns carts; cart and order remain separate aggregates.
  7. Infrastructure: Dokploy handles deployment; use its private networks and persistent services. Choose Redpanda when self-hosting for simpler Kafka-compatible operation unless Dokploy’s environment already provides Kafka.
  8. Initial reliability targets: use the template SLOs below until traffic teaches better values.

Research basis

This plan adapts established guidance rather than copying any one company’s topology. Large-company systems reflect their traffic, teams, regulation, and years of operational tooling; this document keeps the underlying reliability patterns while delaying scale-specific machinery until measurements justify it.
